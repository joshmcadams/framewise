# 17 — Packaging, CI render smoke, scaffolder (and the publish question)

**Status:** 17a–d ready · **17e BLOCKED on item 00** (provenance & licensing)
**Effort:** M · **Depends on:** 17e → **00**; 17a–d → any subset
**Unblocks:** other people actually using this

## Audit verdict

One factual correction and one strategic question.

**Correction: CI already exists.** `.github/workflows/ci.yml` runs `npm ci &&
npm run verify` on Node 20.x and 22.x for pushes to `main` and all PRs. The
first draft's "there's no CI" was wrong, and it matters because it changes what
this item is: not "add CI", but **"add the render smoke job CI is missing"** —
which is the valuable half, since `verify` never launches Chrome or ffmpeg and
therefore never exercises the renderer. Everything renderer-related in this repo
is verified on one Mac, by hand. That is the real gap.

**Strategic question: is publishing to npm actually the goal?** This is an
educational reimplementation that deliberately mirrors an upstream project's
API surface and naming. Publishing a package under a name derived from that
project is an identity/licensing judgment, not an engineering one — and it is
the user's call, not an executor's. Note that **most of this item's value does
not require publishing**:

| Sub-item                  | Requires publishing?           | Value                                                     |
| ------------------------- | ------------------------------ | --------------------------------------------------------- |
| CI render smoke job       | no                             | **highest** — catches renderer regressions on a second OS |
| `npm pack` file-list gate | no                             | high — the packaging rule in `AGENTS.md` becomes enforced |
| Scaffolder / template     | no (works from a git template) | medium                                                    |
| Templates gallery         | no                             | medium — dogfoods the renderer as a regression asset      |
| npm publish               | **yes**                        | adoption, and it is irreversible in practice              |

**Recommendation:** ship 17a–d now, and treat 17e as a separate decision with a
separate plan.

## 17a — CI render smoke job · the valuable half

Add a second job to the existing workflow (do not replace `verify`):

```yaml
render-smoke:
  runs-on: ubuntu-latest
  steps:
    - checkout, setup-node 22, npm ci
    - install ffmpeg (apt or a setup action)
    - render: --list # no browser needed
    - render: --comp HelloWorld --still 45 --out out/still.png
    - render: --comp HelloWorld --props '{"title":"CI"}' --out out/ci.mp4
    - ffprobe assertions: codec, pix_fmt, dimensions, duration
    - render again at -c 1 and -c 4; assert the two sha256 lines are equal
```

- Chrome: once item 03 lands, the job needs no browser setup at all — the
  renderer downloads its pinned build and CI caches it. That is a strong argument
  for doing 03 first, and worth stating in 03's own value case.
- Keep the composition short to bound minutes; `HelloWorld` at 150 frames is fine
  at `-c 4`.
- **This job will find things.** Ubuntu is a different font stack and a different
  Chrome build from the Mac everything was verified on. Expect the first run to
  fail, and treat what it finds as the item's real output.

## 17b — `npm pack --dry-run` file-list gate

`AGENTS.md` already states the rule ("a packaging change is not done until
`npm run verify && npm pack --dry-run` shows the right file list… run after
BOTH `build` and `build:lib` since they share `dist*`"). Make it a **test**
rather than a remembered procedure: a script that runs both builds, runs
`npm pack --dry-run --json`, and diffs the file list against a checked-in
expected list. Wire it into CI. `package.json` already declares
`files: ["dist-lib"]` and a correct `exports` map, so this is a gate, not a fix.

## 17c — Scaffolder

`npm create framewise-lite` (or, without publishing, a documented
`degit`/template-repo path) producing: vite config, a registry with one
composition, render script wiring, and a README pointing at
`docs/tutorial.md`. **Acceptance: the scaffolded output passes `npm run verify`
unmodified** — and, since the scaffold consumes the library rather than the repo,
it is also the only real test of the published `exports` map.

## 17d — Templates gallery

`templates/` with poster stills **generated by the renderer itself** — dogfooding,
and the posters double as regression assets (a changed poster means something
changed in the render path). Note the existing gallery deliberately does _not_
probe on open (`App.tsx:15-17`); pre-generated posters are exactly what would let
it show real frames without breaking that stance, which makes this a nice pairing
with item 08.

## 17e — npm publish · **BLOCKED ON ITEM 00**

Mechanically unblocked: `package.json` has the exports map, `files: ["dist-lib"]`,
peer deps (`react >= 19`), and `build:lib` produces `dist-lib/framewise-lite.js`
plus types. Only `"private": true` stands in the way.

**Mechanically ready is not the same as clear to ship.** Publishing is
distribution, it is irreversible in practice (npm unpublish is heavily
restricted after 72 hours, and mirrors/caches persist regardless), and this
package both reuses ported code and carries a name derived from its upstream.
`backlog/00-provenance-and-licensing.md` exists to establish the facts that
decide this; **do not work this sub-item until 00 has produced its findings
doc.**

### Pre-publish checklist

Every box must be checked, in order. Boxes 1–4 come from item 00's findings and
are the owner's decisions, not an executor's.

**Licensing and provenance — from item 00**

- [ ] 1. Upstream identified and its license captured verbatim
      (`docs/PROVENANCE.md`)
- [ ] 2. That license **permits redistribution of derivative works under the
      terms you intend to publish under**. If it is source-available with use
      restrictions, or copyleft, stop here — publishing MIT would be
      relicensing code you do not own. Owner decision, with a lawyer if the
      findings warrant one.
- [ ] 3. `NOTICE` / `THIRD-PARTY-LICENSES.md` complete, and **shipped inside the
      package** — confirm it appears in `npm pack --dry-run` output, not just in
      the repo. `files: ["dist-lib"]` currently would **not** include a root
      `NOTICE`; either add it to `files` or emit it into `dist-lib/` at build
      time. This is the single most commonly missed step.
- [ ] 4. Per-file "Ported from…" headers survive the library build into
      `dist-lib` (check `vite.lib.config.ts` minification/comment stripping —
      an attribution comment that the bundler drops is not attribution)
- [ ] 5. `package.json` `license` field reflects reality; add an explicit
      `author`, `repository`, and `bugs`

**Naming — from item 00 step 4**

- [ ] 6. Package name carries no upstream trademark, and the owner has picked it
- [ ] 7. Name is available on npm and not confusingly similar to an existing
      package (search before assuming)
- [ ] 8. README opens by stating plainly what this is — an educational
      reimplementation — and what it is not affiliated with. Clear, prominent,
      first-screen; not a footnote.
- [ ] 9. Rename fully executed if applicable: package name, `src/framewise-lite/`,
      the `window.framewiseLite` seam (`main-render.tsx:29-51`), the
      `/__framewise_extract` mount (`offthread-server.mjs:18`), docs, chapters,
      tutorial, tests — with `npm run verify` green afterwards

**Technical readiness**

- [ ] 10. 17b's `npm pack --dry-run` file-list gate passes, run **after both**
      `build` and `build:lib` (they share `dist*` — `AGENTS.md` packaging rule)
- [ ] 11. Install-from-tarball smoke in a scratch dir renders HelloWorld
      end-to-end, exercising the real `exports` map
- [ ] 12. 17a's CI render smoke is green on Linux, including `-c 1` vs `-c 4`
      hash equality
- [ ] 13. Version and stability policy stated: 0.x, and an explicit note that
      this backlog is actively changing the API surface
- [ ] 14. `README` documents the peer-dependency contract (`react >= 19`) and the
      renderer's external requirements (Chrome, ffmpeg — or item 03's managed
      browser)
- [ ] 15. Support expectations set in the README — a published package attracts
      issues; say what you will and will not maintain

**The publish itself**

- [ ] 16. Dry run first: `npm publish --dry-run`, inspect the file list one more
      time
- [ ] 17. 2FA enabled on the npm account
- [ ] 18. Publish under a `0.x` version with `--access public` if scoped
- [ ] 19. Immediately verify: install the published package fresh in a scratch
      dir and render HelloWorld

### If the answer is "not yet"

Say so **in this file**, with the date and the reason, and keep 17a–d. That is a
perfectly good outcome: the CI render smoke and the pack gate are the two
highest-value pieces here and neither needs publishing. Nothing else in the
backlog is blocked by this decision.

## STOP — decisions the executor must not make alone

1. **Do not flip `"private": false` or run `npm publish`** until item 00's
   findings exist AND every box in the 17e checklist is checked. Boxes 1–4 and
   6 are the owner's decisions, not an executor's.
2. **Do not replace the existing `verify` CI job**; add alongside it.
3. **Do not weaken a CI assertion to make the first Ubuntu run green.** If
   Ubuntu's output differs from the Mac's, that is a finding about the
   determinism scope (see item 03) and belongs in the docs.

## Risks

- **CI minutes** — bound the smoke composition; cache the browser download.
- **Cross-OS rendering differences** — likely, and valuable to discover. The hash
  gate is per-browser-build (item 03); a Linux/Mac difference at the _same_
  Chrome build would be a genuinely interesting finding worth documenting.
- **Scaffolder drift** — a template that stops working is worse than none. Its
  `verify` run in CI is what keeps it honest.

## Verification

- CI green on a clean checkout, both jobs, both Node versions
- Render smoke: `ffprobe` assertions pass; `-c 1` and `-c 4` hashes equal **on
  Linux**
- `npm pack --dry-run` file list matches the checked-in expectation exactly,
  after running both `build` and `build:lib` in sequence (the shared-`dist*`
  trap from `AGENTS.md`)
- Install-from-tarball smoke in a scratch dir renders HelloWorld end-to-end
- Scaffolder output passes `npm run verify` unmodified

**Does not cover:** a green CI render says the pipeline works on Ubuntu; it does
not say the output _looks_ the same as on macOS. If the hashes differ across OSes
at the same browser build, document the finding — do not paper over it by
loosening the assertion.
